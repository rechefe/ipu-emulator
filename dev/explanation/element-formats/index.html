    Element formats¶

    An element format says how the IPU reads the elements of a vector: how many bits each element has and what number those bits stand for. A kernel runs in one format, chosen when it starts. The program is the same in every format; the format decides what its loads, multiplies and accumulations compute.

    The formats¶

    The format sets the element width. Everything else follows from it:

    • Row bytes. An XMEM row holds one element per lane, 128 elements. Its width is 128 × the element bytes.
    • Accumulator type. MULT_RES and R_ACC hold INT32 for the integer formats and FP32 for the float formats.
    • Register element widths. R0, R1 and R_CYCLIC hold elements of the format; R_MASK is the same in every format.
    Format Tag Element bits Exponent bits Mantissa bits Row bytes Accumulator
    INT8 HARDWARE 8 0 0 128 INT32
    E1 HARDWARE 8 1 6 128 FP32
    E2 HARDWARE 8 2 5 128 FP32
    E3 HARDWARE 8 3 4 128 FP32
    E4 HARDWARE 8 4 3 128 FP32
    E5 HARDWARE 8 5 2 128 FP32
    E6 HARDWARE 8 6 1 128 FP32
    E7 HARDWARE 8 7 0 128 FP32
    FP32 EMULATOR 32 8 23 512 FP32
    INT32 EMULATOR 32 0 0 512 INT32

    The table is generated from ipu_isa.formats.

    Hardware formats. INT8 and E1 to E7 are HARDWARE formats: the IPU has them, and the host selects one at run time.

    Emulator formats. FP32 and INT32 are EMULATOR formats: they exist only in the emulator. They run a kernel at full precision, with no 8-bit rounding on the multiply path, so its result can be compared with a full-precision reference such as PyTorch. The assembly and its XMEM row numbers are the same as in the 8-bit formats; each element takes four bytes instead of one.

    How the 8-bit formats encode values¶

    INT8 is a two's-complement byte, -128 to 127.

    E1 to E7 are 8-bit floats. Ex has 1 sign bit, x exponent bits and 7 - x mantissa bits, and its exponent bias is 2x-1 - 1.

    • An exponent of all ones is NaN, whatever the mantissa. There are no infinities.
    • An exponent of zero is a subnormal value: 0.mantissa × 21-bias.
    • E1 has no normal values: its only non-zero exponent is the NaN exponent.
    • E7 has no mantissa bits: every value is a power of two.
    Format Bias Largest finite Smallest normal Smallest subnormal NaN codes
    E1 0 1.96875 none 0.03125 128
    E2 1 3.9375 1 0.03125 64
    E3 3 15.5 0.25 0.015625 32
    E4 7 240 0.015625 0.001953125 16
    E5 15 57344 2-14 2-16 8
    E6 31 1.5 × 231 2-30 2-31 4
    E7 63 263 2-62 none 2

    The table is computed from the element codec, ipu_isa.formats.decode_element.

    Encoding a value into an 8-bit format:

    • Rounding. It rounds to the nearest value, and a tie goes to the even code.
    • Overflow. A value beyond the largest finite value, and an infinity, saturate to the largest finite value of that sign. INT8 saturates to -128 or 127.
    • NaN. NaN encodes as the canonical NaN: exponent all ones, mantissa 1 (0x7F in E7, which has no mantissa bits). INT8 has no NaN, so encoding NaN to INT8 is an error.
    • Negative zero. In E1 to E7, -0.0 keeps its sign bit (0x80).

    Open question

    The special values are not settled. The emulator reads every all-ones exponent as NaN, where IEEE-style decoders read mantissa 0 as an infinity, and its largest E4 value is 240, not the 448 of OCP E4M3. See OQ-19 in Open questions.

    CR scalars¶

    A CR holds 32 bits. MULT.VE, MULT.EE and MULT.RC.VE (with a CR as src) use a CR as a scalar element: they multiply a vector by it. The scalar is the CR's low element-width bits, decoded as an element of the active format:

    Format CR bits Decoded as
    INT8 [7:0] a signed 8-bit integer
    E1 [7:0] an E1 element
    E2 [7:0] an E2 element
    E3 [7:0] an E3 element
    E4 [7:0] an E4 element
    E5 [7:0] an E5 element
    E6 [7:0] an E6 element
    E7 [7:0] an E7 element
    FP32 [31:0] an FP32 element
    INT32 [31:0] a signed 32-bit integer

    So the same CR value stands for a different number in each format. A host that programs a scalar writes it in the kernel's format: the float32 bit pattern of the value in FP32, its 8-bit code in E4.

    CR1 is the exception. It is the hardware constant 1, and as a scalar it reads as 1 in every format (1.0 in a float format), so a multiply by CR1 is an identity multiply whatever the format. This rule holds from E04-28 on; before it, every format read the CR's low byte.

    This program multiplies a vector of ones by CR3, so every element of MULT_RES is the scalar as the format decodes it:

    # Ra (R0 ++ R1) holds 1 in every element, so each MULT_RES element is the decoded scalar.
PROGRAM = """
MULT.VE LR0 CR3 0 LR2 CR15;;
HALT;;
"""
CR3 = 0x3F80_0038  # the float32 1.0 (0x3F800000) plus 0x38

    The test that runs it checks element 0 of MULT_RES in each format:

    EXPECTED = {
    ElementFormat.INT8: 56,  # the low byte, 0x38, as a signed byte
    ElementFormat.E4: 1.0,  # 0x38 as an E4 element: exponent 7, bias 7, mantissa 0
    ElementFormat.FP32: 1 + 56 * 2**-23,  # all 32 bits as a float32: 1.0 plus 56 ulps
    ElementFormat.INT32: 1_065_353_272,  # all 32 bits as a signed integer
}

    Selecting a format¶

    The format is emulator configuration, not a CR value. Choose it when you construct the state, or reset the state into another format:

    from ipu_emu.ipu_state import IpuState
from ipu_isa.formats import ElementFormat

state = IpuState(fmt=ElementFormat.INT8)

# Or return an existing state to reset, in another format.
state.reset(ElementFormat.E4)

    state.fmt cannot be assigned. An unknown format raises ConfigurationError when the state is built, never while a program runs.

    A kernel lists its formats in its kernel.toml's [kernel] formats. A case can list a subset in its own formats; otherwise it runs in each of the kernel's formats.

    XMEM layout per format¶

    An XMEM operand in assembly (offset + base) is a row number in every format. A row is 128 elements, so its width depends on the format: row r starts at byte r × 128 in the 8-bit formats and r × 512 in FP32 and INT32. A program reaches the same row in every format. The 8-bit formats address only the first 16384 rows of XMEM.

    • LD.MULT reads one row (128 elements) into R0 or R1.
    • LD.MULT.CYCLIC reads one row into one of the four slots of R_CYCLIC. Its index must be a slot boundary: 0, 128, 256 or 384.
    • Register indices count elements. rc_idx, ra_idx and the cyclic index are element indices in every format, so a program indexes its registers the same way whatever the format.
    • Element data in XMEM is little-endian float32 or int32 in FP32 and INT32, and one byte per element in the 8-bit formats.

    The kernel harness packs each tensor for the case's format (ipu_harness.packing). An accumulator output (ST.ACC) is stored in the format's accumulator type, four bytes per element: in an 8-bit format one of its vectors spans four rows.

    How FP32 and INT32 compute¶

    • Multiply and accumulate. FP32 uses IEEE float arithmetic. INT32 multiplies and adds with 32-bit two's-complement wrap, and AGG.* reduce as 32-bit signed integers.
    • Masks. The mask-and-shift on MULT_RES is the same in every format: each of the 128 mask bits gates one element.
    • ACTIVATE.QUANTIZE writes the activated elements to POST_AAQ_REG without quantizing them, unless the state was built with AaqOptions(quantize_output=True) (from ipu_emu.activations). R_ACC keeps the full results; ST.ACC stores them. The AaQ stage is a placeholder: see OQ-20, OQ-22 and OQ-34 in Open questions.

    Arithmetic events¶

    An accumulator overflow or a NaN result is an arithmetic event, not a fault: see Arithmetic events. What the emulator does on an FP32 overflow is OQ-18 in Open questions.
