# Convolutions

Eleven kernels covering `conv2d` (standard, depthwise, and pointwise/1x1
variants, each with a bias+ReLU twin) plus a standalone `residual_add`. They
split along three axes -- kernel size (1 vs 3), grouping (plain vs
depthwise), and stride (1 vs 2) -- and within stride-2 depthwise, further by
how the input width packs into the 128-element datapath.

All are **wide-vector FP32 mode only** (`wide_vector_debug=True`). They have
no narrow (INT8/FP8) variant -- see [FP32 registry migration](../app-coverage.md)
for why INT8 was retired as the live code path (preserved on the
`conv-int8-snapshot` branch).

## Picking one

```bash
python -m ipu_apps.convolutions_universal --in-channels 32 --out-channels 32 \
    --kernel-size 3 --stride 1 --padding 1 --groups 32 --height 64 --width 64
```

## Kernel size and grouping

Every kernel is fixed to exactly one `(kernel_size, groups)` combination --
`kernel_size` is never 2, 4, or anything but 1/3, and `groups` is never
between 1 and `in_channels` (true grouped convolution, as opposed to plain or
fully-depthwise, has no kernel at all). `dilation` must always be 1.

## The 128-lane width ceiling

Every FP32 wide-vector chunk holds 128 elements. A convolution kernel packs
one or more spatial rows per chunk (`rows_per_chunk = 128 // cols`, so `cols`
must divide 128), which is why width is capped at 128 for every kernel except
`conv_universal_wide384` (built for exactly width=384, spanning 3 chunks per
row) and the fixed-shape `conv_first_layer`.

## Taps are hand-unrolled, not looped

Every 3x3 kernel here (`conv_universal`, `depthwise_conv_universal`, and
their `_bn_activation` twins) processes its 9 taps as 9 separate, individually
written VLIW cycles in the `.asm` -- there is no runtime loop over taps, and
no Jinja macro generating them from a template either; each tap's instruction
words are hardcoded in sequence.

This is a direct consequence of the taps not being identical work. Each tap
reads a different spatial offset (`kr, kc` relative to the output pixel, see
the tap-offset table in `conv_universal.asm`'s header comment), so the offset
arithmetic differs tap to tap; several taps additionally double as a load
cycle for an upcoming channel or a store/activation cycle (tap 1 doubles as
the `r_acc` reset via `acc.add.first`, the last tap fuses in
`ACTIVATE.QUANTIZE`). A runtime loop body would have to be the union of all
of that -- branch-selected per iteration -- which costs a branch and a
mispredict-adjacent stall every cycle instead of every 9. Unrolling lets each
cycle issue exactly the slots it needs and nothing else, which is what gets
these kernels to 9 cycles/channel (see [Cost](#cost)) in the first place.

Pointwise's single tap has no such structure to unroll -- one MULT/ACC pair
per channel already is the loop body.

## Standard and pointwise convolution

`conv_universal` and `pointwise_conv_unified` (plus their `_bn_activation`
twins) share the same chunk-interleaved input/output layout described below;
they differ in tap count (9 taps for a 3x3 kernel vs. 1 for pointwise) and
in how weights are packed per channel. Both walk a super-block of packed
kernel taps per output channel and stream spatial chunks through the same
walking-pointer pipeline established for the depthwise apps (see
[Techniques & workflow](../adding-applications.md)).

`conv_universal_wide384` exists because 384 doesn't divide 128 the way every
other supported width does -- 3 chunks (384 = 3 x 128) are needed per spatial
row instead of one, so its packing and walking logic is a distinct kernel
rather than a parameterization of `conv_universal`.

## Depthwise convolution

`depthwise_conv_universal` runs 9 cycles/channel: 9 weight taps, with
`ACTIVATE.QUANTIZE` fused into tap 9's own cycle (no standalone activation
cycle) and tap 1 doubling as the `r_acc` reset via `acc.add.first`. The
`_bn_activation` twin folds in a per-channel bias and unconditional ReLU at
the same cycle count.

### Stride-2 depthwise: three kernels, one gap closed

Stride-2 depthwise decimates both spatial dimensions by 2 after the same
full-resolution convolution stage 1 already computes. All three stride-2
kernels share this two-stage design -- an unmodified `depthwise_conv_universal`
stage 1, then a stage-2 pass using `ACC.STRIDE` to decimate -- because
`ACC.STRIDE` always writes exactly 32 elements to one of 4 fixed 32-element
slots in `r_acc`, and the only store instruction (`STR_POST_AAQ_REG`) always
writes a full 128-element chunk. Those two fixed-width constraints are why
three separate kernels exist instead of one parameterized pass:

- **`depthwise_conv_stride2_128`** -- width=128 (no packing: one input row
  per chunk). Two `ACC.STRIDE` calls per row pair fill one output chunk.
- **`depthwise_conv_stride2_narrow`** -- width in `{16, 32, 64}` (multiple
  packed rows per chunk). Groups **4** stage-1 row-groups per output chunk,
  so `height` must be a multiple of `4 * rows_per_chunk`.
- **`depthwise_conv_stride2_16`** -- the fixed `height=width=16` shape,
  where the true output (8x8 = 64 elements/channel) is only **half** a
  chunk, and `depthwise_conv_stride2_narrow`'s 4-row-group grouping has no
  valid instance (only 2 stage-1 row-groups exist at this height). Rather
  than pad the unused half, this kernel packs **two adjacent channels** per
  output chunk -- channel `2p`'s two row-groups fill `r_acc[0:64]`, channel
  `2p+1`'s fill `r_acc[64:128]` -- so nothing is wasted.

    This kernel exists specifically because `height=width=16` is MobileViT-S's
    deepest MV2 downsample shape, and no existing kernel covered it (see
    [Application coverage](../app-coverage.md) for how that gap was found and
    closed).

None of the stride-2 kernels are cycle-optimized: each is an unfused
two-stage composition (full-resolution conv, then a separate decimation
pass), traded for lower implementation risk over a fused single-pass design.

## `residual_add`

A standalone elementwise `FP32 + FP32 -> FP32` kernel, registered under its
own `residual_add` operation (not `conv2d` -- it takes two independent
tensor inputs, no weight). Same wide-vector chunk-per-channel layout as every
other kernel here; sized for MobileViT S's residual stages (64x64x64 through
8x8x160).

## Data layout

Every app reads and writes **raw, unpadded `[channels, height, width]`
float32** (or `[channels, rows, cols]` for `residual_add`, which has no
spatial structure to pad): the output file has the same layout convention as
the input file -- the same contract `test_softmax_layout_roundtrip.py`
enforces for softmax.

Internally, every kernel repacks into a **chunk-interleaved** layout: spatial
rows are grouped `rows_per_chunk = 128 // cols` per 128-element chunk, chunks
grouped by channel. This is strictly internal -- the harness packs on the way
in (`setup()`) and unpacks on the way out (`teardown()`/`run()`); no caller
ever sees it. The three stride-2 depthwise kernels additionally repack their
final output (row-pairs, row-group quads, or channel-pairs respectively) back
into the true tensor shape before writing `output_path`.

## Cost

From the committed benchmarks (`results.md` beside each kernel):

| Kernel | Config | cycles | MULT util |
|---|---|---:|---:|
| `conv_universal` | 64x64, ic=32, oc=32 | 318,564 | 92.9% |
| `conv_universal_bn_activation` | 64x64, ic=32, oc=32 | 318,564 | 92.9% |
| `conv_first_layer` | 256x256x3 -> 128x128x16 | 286,532 | 41.4% |
| `conv_universal_wide384` | 384x16, ic=3, oc=4 | 22,278 | 24.1% |
| `pointwise_conv_unified` | 64x64, ic=128, oc=64 | 289,065 | 90.7% |
| `pointwise_conv_unified_bn_activation` | 64x64, ic=128, oc=64 | 293,161 | 90.1% |
| `depthwise_conv_universal` | 64x64x64 | 19,686 | 93.6% |
| `depthwise_conv_universal_bn_activation` | 64x64x64 | 21,734 | 94.2% |
| `depthwise_conv_stride2_128` | 128x16 | 24,941 | 78.3% |
| `depthwise_conv_stride2_narrow` | 16x32x24 | 1,901 | 109.6% |
| `depthwise_conv_stride2_16` | 16x16x320 (MobileViT-S shape) | 9,448 | 67.8% |

Two things worth reading off this. `conv_first_layer`'s low MULT utilization
(41.4%) reflects its 3-input-channel first layer -- there simply isn't enough
work per cycle to keep the datapath full at that channel count, unlike the
16+-channel steady-state layers. And `depthwise_conv_stride2_narrow`'s >100%
util figures are not a bug: `mult_active_cycles` counts stage 1 and stage 2
combined against the combined cycle total, and stage 2's identity
`MULT.VE` passthroughs (needed to route data into `ACC.STRIDE`, which reads
`MULT_RES` not `R_ACC`) count as active cycles despite doing no real
multiply-accumulate work, inflating the ratio at very small configs where
stage 2 is a larger fraction of the total.

Run them yourself with:

```bash
python -m ipu_apps.convolutions_universal.<family>.<app>.benchmark.benchmark
```

Every benchmark config checks correctness against real
`torch.nn.functional.conv2d` (tolerance-based, since IPU FP32 accumulation
order differs from PyTorch's), so a benchmark cannot report a fast wrong
answer.

## Using one directly

```python
from ipu_apps.convolutions_universal.depthwise.depthwise_conv_universal import (
    DepthwiseConvUniversalApp,
)

app = DepthwiseConvUniversalApp(
    inst_path="depthwise_conv_universal.bin",
    input_path="input.bin",      # raw [channels, height, width] float32
    kernel=weights,               # np.ndarray [channels, 3, 3] float32
    output_path="output.bin",
    height=64, width=64, channels=256,
)
state, cycles = app.run()
```

Or let the registry construct the call for you -- see
[Application coverage](../app-coverage.md).
