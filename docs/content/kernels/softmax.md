# Softmax

Five kernels covering every 1-D softmax shape. They differ in which direction
the reduction runs and how the reduced length relates to the 128-element datapath —
but they share one formulation and one four-pass structure, so understanding one
gets you most of the way through the others.

All five are **wide-vector FP32 mode only** (`wide_vector_debug=True`). They
build on `exp2` and reciprocal over an FP32 vector path and have no narrow
(INT8/FP8) variant.

## Picking one

Don't pick by hand — ask the registry:

```bash
python -m ipu_apps.softmax --shape 32,300 --dim 1
```

The routing below is generated by probing the kernels, so it always matches
what the registry actually answers.

**Along each row** (`torch.softmax(x, dim=1)` on a `(rows, n)` tensor):

```
n 1..127        softmax_rows_partial
n = 128         softmax_rows
n 129..         softmax_rows_long
```

**Down each column** (`dim=0` on a `(rows, width)` tensor):

```
width 1..64     softmax_columns_packed
width 65..      softmax_columns
```

Row count never affects routing: every row kernel loops internally.

## The shared formulation

The IPU's activation unit provides `exp2`, not `exp`. Rather than approximating
`e^x`, the kernels reformulate in base 2:

```
softmax(x_i) = 2^(c * (x_i - xmax)) / SUM_j 2^(c * (x_j - xmax))     c = log2(e)
```

which is exactly equal to the usual definition, because `2^(c*d) == e^d`. The
constant `c = log2(e)` lives in a resident 128-element vector, so applying it costs
one multiply.

Subtracting `xmax` is the standard numerical-stability step: it makes the
largest exponent zero, so nothing overflows. It is free here — `ACC.SUB` against
CR1 does it in the accumulate slot.

Every kernel then runs the same four passes:

1. **max** — per-row (or per-column) maximum
2. **numerators** — `2^(c*(x - xmax))`, written out
3. **sum** — reduce the numerators
4. **normalise** — multiply by the reciprocal of the sum

## The row kernels

The reduction runs *along* a row, collapsing 128 elements to one scalar. That is
what `AGG` does, and the per-row scalars are then fanned back out.

### `softmax_rows` — exactly 128 elements

The straightforward case: one row fills the vector exactly. No packing, no
chunking, no padding.

### `softmax_rows_partial` — shorter than 128

Several logical rows share one 128-element chunk. The partition size `ps` is the
next power of two ≥ N (clamped to [16, 128]), so `P = 128 / ps` rows fit per
chunk:

| N | ps | rows per chunk |
|---|---|---|
| 65–128 | 128 | 1 |
| 33–64 | 64 | 2 |
| 17–32 | 32 | 4 |
| 1–16 | 16 | 8 |

To reduce partition `p`, `MULT.RC.VV` reads `r_cyclic` at element offset `p*ps`,
which slides that partition down to elements `0..N-1`; a masked `AGG` then reduces
exactly those elements. Pass 4 reverses the slide to re-pack the results.

!!! note "Why Pass 4 needs a mask"
    `ACC.ADD` writes all 128 elements unconditionally, and `MULT.RC.VE` leaves
    other rows' real data in the elements outside the current partition — so
    without masking, partitions overwrite each other's results. Each partition
    therefore gets its own `R_MASK` slot restricting the write to its own element
    range.

    Because `mask_offset` is a compile-time immediate, the per-partition
    sequence is unrolled with Jinja (one block per P value) rather than written
    as a runtime loop, with a runtime branch selecting the right block.

### `softmax_rows_long` — longer than 128

A row spans several chunks, so the max and the sum span them too. Each pass
keeps a **running** per-row scalar: `AGG.*.FIRST` on the first chunk, then plain
`AGG.*` on the rest, combining into the same accumulator slot.

When `N` is not a multiple of 128 the last chunk is partial and reduces with
`valid_elements = tail` instead of 128. When `N` *is* a multiple of 128 there is
no tail chunk at all.

## The column kernels

Column softmax is the **transpose** of row softmax, and the difference is
structural rather than cosmetic.

In row softmax the reduction collapses the elements of one vector to a scalar. In
column softmax every element is an *independent column*, and the reduction runs
**across rows, staying in-element**. So there is **no `AGG` and no fan-out**: the
per-column max and sum are themselves full 128-element vectors, accumulated with
`ACC.MAX`/`ACC.ADD` down the rows.

That also removes the row-group cap — per-column scalars are full vectors, not
one slot per row — so row count is an ordinary loop bound.

### `softmax_columns` — width ≥ 65

Width is padded up to a multiple of 128. Padding elements are simply *separate
columns* that happen to be all-zero; they never enter a real column's reduction,
and they are dropped on read-back.

Widths that are not a multiple of 128 leave elements idle. The registry reports
this per query rather than as a generic warning — width 100 says *"28 of every
128 elements sit idle (78% utilisation) … runs at the cost of width 128."*

### `softmax_columns_packed` — width ≤ 64

Below 65, several whole rows fit in one vector (`rows_per_vec = 128 / padded
width`), so the kernel packs them and reduces in two stages: a partial reduce
down the vector, then a **cross-group fold** that combines the groups using
cyclic shifts.

Padding is filled with a large negative value rather than zero, so it loses
every max comparison and contributes nothing to the sums — without that, the
fold would mix padding into real columns.

## Row counts

Per-row scalars hold one slot per row in a single 128-element vector, so at most
128 rows can be in flight. Every row kernel therefore processes rows in
**groups** of at most 128, running all four passes per group before advancing.

This is a correctness requirement, not bookkeeping. The row index feeds
`MULT.RC.VE`'s scalar-select and `AGG`'s destination slot, both of which index
R0 for 0..127 and switch to R1 — never loaded in these passes — at 128.
Restarting the index each group makes that unreachable. Group size is exact
(`min(128, rows_left)`), so no padding row is ever processed.

## Data layout

Every app reads and writes **row-major `(rows, cols)` float32**: the output file
has the same layout as the input file.

Internally the layouts differ considerably — `softmax_rows_partial` packs P rows
per chunk and pads the row count; `softmax_rows_long` pads a tail chunk;
`softmax_columns` pads the width — but none of that reaches the files. The
harness packs on the way in and un-packs on the way out.

## Cost

From the committed benchmarks (`results.md` beside each kernel):

| Kernel | Config | cyc/row | MULT util |
|---|---|---|---|
| `softmax_rows` | 128 rows | 18.15 | 27.6% |
| `softmax_rows_partial` | n=16, 512 rows | 18.43 | 27.1% |
| `softmax_rows_long` | n=200, 200 rows | 48.17 | 20.8% |
| `softmax_columns` | width 128, 128 rows | 19.18 | 26.1% |
| `softmax_columns_packed` | width 32, 100 rows | 5.25 | 25.5% |

Two things worth reading off this. The packed column kernel is far cheaper per
row because it processes several rows per vector. And the group loop costs
essentially nothing: `softmax_rows_partial` at n=128 runs 28.23 cyc/row over 300
rows versus 28.48 over 50, despite crossing group boundaries.

Run them yourself with:

```bash
python -m ipu_apps.softmax.<app>.benchmark.benchmark
```

Every benchmark config checks correctness against NumPy as well as reporting
cycles, so a benchmark cannot report a fast wrong answer.

## Using one directly

```python
from ipu_apps.softmax.softmax_rows_long import SoftmaxRowsLongApp

app = SoftmaxRowsLongApp(
    inst_path="softmax_rows_long.bin",
    input_path="logits.bin",      # rows * N float32, row-major
    output_path="probs.bin",      # same layout
    rows=8,
    n=300,
)
state, cycles = app.run()
```

Or let the registry construct the call for you — see
[Application coverage](../app-coverage.md).
