Where a row's format lives

An XMEM row written by AaQ is 128 bytes of elements plus a 16-bit metadata word. To turn those bytes back into numbers, a reader needs a third thing that is in neither: the table's format.

The job of the scale

AaQ takes 128 FP32 values from R_ACC and writes 128 bytes. One byte cannot cover FP32's range, so the 128 elements share one exponent, the row's scale s. Each element then stores only how far it sits below that scale, plus a few mantissa bits.[AaQ §5.1]

AaQ computes s as the largest raw FP32 exponent in the row and stores it as e8m0: an 8-bit exponent, a power of two with no mantissa.[AaQ §5.1]

The industry calls this block scaling. The OCP Microscaling (MX) standard shares one E8M0 scale across 32 elements;[CUTLASS] [AWS Neuron] AaQ shares one across a whole 128-element row.

Why the metadata alone is not enough

Take a row whose largest value is 3.2. In FP32, 3.2 = 1.6 × 21, a biased exponent of 128, so s = 128. One element is 0.4 = 1.6 × 2−2, biased exponent 125, which sits E = 128 − 125 = 3 binades below the scale.

In an E4M3 table (fe = 4), AaQ stores exponent field 3 and rounds 0.6 to 3 mantissa bits (5/8). The byte is 0 0011 101 = 0x1D, which decodes to 1.625 × 2128−127−3 = 0.40625.

Now read the same byte with the same scale but fe = 2. The bits split differently and give 3.8125. Change fe below and watch the violet field move.

Decode a byte

The scale says where the row's values are. The table's fe says how to split each byte. A reader needs both, and they come from different places.

Exception, dynamic tables. When format[8] = 1, the table fixes only "signed, 8 bits". AaQ picks E1M6 or E2M5 for each row and records the choice in that row's dynamic_exponent bit. So in a dynamic table, fe comes from the metadata word instead.[AaQ §5.1.1]

Explain it back

In two sentences, tell an RTL engineer why a row's metadata word alone cannot decode the row. Type it, then compare.

The metadata gives the row's scale, which says where its values sit, but not how each byte splits into exponent and mantissa bits. That split, fe, belongs to the table's format; only a dynamic table moves it into the row, through dynamic_exponent.

What this means for the emulator

Today the emulator's XMEM is a flat byte array, and one element format applies to the whole run (ADR 0003). Matching the specs needs at least these pieces. All of them are still open in the design session:

  • XMEM: a 16-bit metadata word beside every 128-byte row.
  • Configuration: a table format for each input and output region, since the emulator has no cache tables.
  • AaQ: the spec's ACTIVATE.QUANTIZE (scale, encoding, dynamic choice) and the LUT load. Today's version moves to an emulator-only slot so old kernels keep working.
  • POST_AAQ_REG and ST.AAQ: 128 bytes plus the metadata word, written together.
  • LD and MULT: carry each row's metadata into the registers and expand the elements to FP32 before multiplying.
Where the spec stops

No document defines how MULT expands a scaled row to FP32. The decoder on this page inverts the quantizer of AaQ §5.1; treat it as a proposal. The spec also contradicts itself on fe = 0 (an INT8-like table): §3.3 allows it, §5.1 says fe is at least 1.
