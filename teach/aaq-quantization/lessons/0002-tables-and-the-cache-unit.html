Tables, and how a load finds its table

A table describes one array's trip between DRAM and XMEM, including its format. The RISC-V host writes the tables, the cache unit stores them, and the IPU's cache agent reads a copy to decide whether each access can proceed.

What a table is

A table is the cache unit's record for one array, such as a weight matrix, an input activation or an output.[cache unit §5] It holds:

FieldBitsMeaning
table_id4The number the IPU sends with each address. 16 possible tables.
type2read_only, write_only, read_after_write or scratch_pad, seen from the IPU.
dram_base_address, size32, 16Where the array lives in DRAM, and how big it is, in bank-sized units (128 KB).
xmem_bank_list, xmem_num_of_banks16×4, 4Which of the 16 XMEM banks this table cycles through, in order.
jump_back, repetitions16, 16When a bank can be freed, and how many passes the kernel makes over the table.
format9The AaQ element format of every row in the table (lesson 1).

How many tables a kernel has

  • One table per array the kernel touches. A fully connected layer might use three: weights, input, output. A kernel that keeps intermediate rows in XMEM adds a scratch_pad table. The compiler gives each symbolic name (W_Table, Xout_Table) a number 0–15.[cache unit §7]
  • At most 16, because table_id is 4 bits.
  • The kernel's tables form one table set. The cache unit holds two table sets, one per IPU context: the running kernel's and the next kernel's.[CU-10]

A context is one IMEM bank, one CR bank and one table set. The active_ctx bit selects all three at once, so while kernel N runs from context 0, the host loads kernel N+1, with its tables, into context 1.[execution flow]

Who holds what

Writes

RISC-V host

  • Writes the kernel into IMEM bank k and CR bank k.
  • Writes table set k, then commits it.
  • Sends ARM. It succeeds only after the commit.
Stores and moves

Cache unit (outside the IPU)

  • Holds both table sets; raises tables_valid[k] on commit.
  • DMA fills and drains the 16 XMEM banks by the tables.
  • Rejects table writes while context k is locked.
Reads and decides

Cache agent (an IPU stage)

  • Gets a read-only copy of both table sets: the tbl_view input.
  • Decides hit or miss for each word's load and store.
  • On a miss, stalls CTRL and requests the bank.

Sources: memory access, IPU-MEM-1 to 12, interfaces, CU-10 to CU-18.

So the answer to "does it sit in the cache agent?" is: the tables are stored in the cache unit; the cache agent inside the IPU only reads them.

How a load names its table

An instruction never names a table. CTRL adds a base CR and an offset LR, and the sum is the row address.[memory access] The table is part of that address:

row_address = CR[base] + LR[offset] = { table_id[23:20], page[19:10], row[9:0] }

The open-questions page proposes that the base CR carries the table id in its top bits.[OQ-8] The host sets CR3 = 0x200000 once, and every ST.AAQ LRn CR3 then lands in table 2, whatever the LR holds. Each page is one XMEM bank of 1024 rows. The cache agent compares the tag {ctx, table_id, page} with the tag the bank holds.

Split an address

Try LR = 1023, then 1024: the access moves to the next page, so the next bank of the table.

Where the format comes in

  • Reading: a load's address gives its table_id; that table's format in tbl_view tells MULT how to split each byte. The row's metadata word arrives with the data.
  • Writing: AaQ needs the destination table's format when it quantizes. The table is known only from the ST.AAQ address. The AaQ spec lists format as an input but does not say where it comes from.

Tables in the emulator today

The emulator has no cache unit, no tables and no stalls: XMEM is one flat byte array. The closest thing to a table is a kernel's kernel.toml. Each array is declared under [inputs] or [outputs], and [abi] binds it to a base CR, for example y = "CR3" in kernels/attention/qk_scores_64x48. One array with one base CR is the role a table plays, so the natural home for each array's AaQ format is that array's entry.

Explain it back

In three sentences, tell a colleague how an LD.MULT finds its table and where that table's description is kept.

CTRL adds the base CR and the offset LR; the top 4 bits of the sum are the table id, the rest are page and row (OQ-8 proposal). The table's description, including its format, is in the active table set in the cache unit, written and committed by the RISC-V host before the kernel started. The IPU's cache agent reads a copy of it (tbl_view) to check the bank tag and stall on a miss.

Where the specs stop
  • Where the table id sits in the row address is a proposal (OQ-8).
  • The width and signals of tbl_view are open (OQ-15).
  • The cache-unit spec has its CRM check tags; the requirements give that job to the IPU's cache agent. Action A-3 updates the cache-unit spec.
  • Which table's format AaQ uses when it quantizes is not specified.
