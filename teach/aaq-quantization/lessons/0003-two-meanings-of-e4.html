One E4: NX8

The hardware has one 8-bit float family, NX8 e1–e7. An NX8 element stores how many binades it sits below its row's scale. The emulator's own E1–E7 are an older, unscaled encoding that matches no hardware format, and they are being replaced by NX8.

Spec update (master 0511213)

The MULT architecture spec now defines the NX8 decode, and the AaQ architecture spec defines the encode. Both match the formula lessons 1 and 4 use. Decision: the emulator replaces its E1–E7 with NX8; only 3 kernels use E1–E7.

NX8 e4: a range that follows the row

AaQ encodes each element as Exp = s − e, its distance below the row's scale.[ARCH AaQ §4.3.2] MULT decodes it back to FP32 with the same rule.[ARCH MULT §3.2.1] A larger field means a smaller value.

Exponent fieldValue (signed e4, W = 8, row scale s)
0±(1 + M/8) · 2s−127, the row's top binade
1 … 14±(1 + M/8) · 2s−127−Exp
15 (all ones)±(M/8) · 2s−127−14, the clamp branch

Raise the row's scale by 1 and every value in the row doubles. The 15 binades the field covers move to wherever the row's values are. Zero is the clamp branch with M = 0: 0x78.

The format itself (signed or not, fe, width, static or dynamic) comes from a quantizion_format CR operand of the instruction in the architecture specs, and from the table in the microarchitecture spec (spec audit #3, #17).

The old emulator E4, being retired

The emulator's E1–E7 (ADR 0003) are ordinary small floats. The exponent field is biased: the format subtracts a fixed bias, 2x−1 − 1 (7 for E4), and reads no scale.[formats.py]

Exponent fieldValue (old emulator E4)
0±(M/8) · 21−7, subnormal
1 … 14±(1 + M/8) · 2Exp−7
15 (all ones)NaN

Its range is fixed, 2−9 to 240, in every row. No hardware stage produces or reads it, so it goes. The kernels linear/fully_connected, conformance/vector_tour and elementwise/scale move to NX8 and get new goldens.

Encode by hand

Write the byte. Method: write the value as 1.f × 2p. NX8: exponent field = (s − 127) − p. Mantissa = f × 8, rounded. Tasks 5 and 6 use the old emulator E4 (field = p + 7) for contrast only.

Explain it back

In two sentences, tell an emulator developer why the emulator's E4 must change rather than live beside NX8 under another name.

The hardware has one E4, NX8 e4, which counts binades down from a per-row scale; the emulator's E4 is a fixed-range biased float that no stage produces or reads, and the same byte means a different number in each (0x78 is 0 in NX8 and NaN in the old format). Keeping both would let kernels pass in the emulator with data the hardware would read differently, so the emulator switches to NX8 and the 3 kernels that used the old format get new goldens.

What this means for the emulator

  • One NX8 codec. One encoder and decoder in ipu_isa, shared by the AaQ quantizer, MULT's decode and the kernel harness that packs test data.
  • Every NX8 read needs the metadata word. The XMEM metadata store and per-register metadata come first.
  • Three kernels move. fully_connected, vector_tour and elementwise/scale switch to NX8; their goldens change, and the PR says why.
  • ADR 0003 is superseded where it defines E1–E7; a new ADR records NX8.
Where the specs stop
  • ARCH AaQ writes NaN for inactive elements and names NX8 inf, but no spec defines either encoding (audit #13, #22).
  • The quantizion_format CR has different layouts in the AaQ and MULT architecture specs (audit #17).
  • No behaviour for negative inputs to an unsigned format.
