Two meanings of "E4"

The emulator's E4 and AaQ's E4M3 split a byte the same way: 1 sign bit, 4 exponent bits, 3 mantissa bits. They read the exponent field in opposite directions, so the same byte means different numbers.

The emulator's E4: a fixed range

The emulator's E1–E7 formats are ordinary small floats. The exponent field is biased: the format subtracts a fixed bias, 2x−1 − 1 (7 for E4). A larger field means a larger value.[formats.py]

Exponent fieldValue (E4)
0±(M/8) · 21−7, subnormal
1 … 14±(1 + M/8) · 2Exp−7
15 (all ones)NaN

Every E4 byte means the same number in every row: the range is fixed, from 2−9 to 240. One format applies to the whole run (ADR 0003).

AaQ's E4M3: a range that follows the row

AaQ stores Exp = s − e, the number of binades an element sits below its row's scale.[AaQ §5.1] A larger field means a smaller value.

Exponent fieldValue (E4M3, row scale s)
0±(1 + M/8) · 2s−127, the row's top binade
1 … 14±(1 + M/8) · 2s−127−Exp
15 (all ones)±(M/8) · 2s−127−14, the clamp branch

Raise the row's scale by 1 and every value in the row doubles. The 15 binades the field covers move to wherever the row's values are.

Encode by hand

Write the byte. Method: write the value as 1.f × 2p. Emulator E4: exponent field = p + 7. AaQ: exponent field = (s − 127) − p. Mantissa = f × 8, rounded.

Explain it back

In two sentences, tell an emulator developer why "E4" cannot be one enum value for both legacy kernels and AaQ tables.

The emulator's E4 is a fixed-range float with a biased exponent, while AaQ's E4M3 counts binades down from a per-row scale, so the same byte gives different values (0x78 is NaN in one and 0 in the other). Decoding AaQ data also needs the row's scale from the metadata word, which the emulator's E4 never reads.

What this means for the emulator

  • Two decoders. MULT reads a row with the emulator's Ex when the row has no AaQ table format, and with the scale-relative decode when it has one.
  • Distinct names. Code and docs need a name that tells the two apart, for example "AaQ E4M3" or "scaled E4M3" against "E4". Today's ElementFormat.E4 keeps its meaning, so legacy kernels and their goldens stay as they are.
  • Unsettled details become decisions. The tie rule, ±inf and NaN inputs, and fe = 0 all need an answer before the emulator can match RTL bit for bit.
Where the spec stops
  • Zero as 0x78 follows from §5.1 (FP32 inputs are "always treated as normalized") but the spec never states it.
  • §5.1 rounds "to nearest" without a tie rule. Only the dynamic selection terms (§5.1.1) round half up.
  • No behaviour for ±inf or NaN inputs (OQ-22), and none for negative inputs to an unsigned format.
