The activation LUT and the LUT load

AaQ computes three activations directly and the other four through a lookup table inside the stage. The kernel fills that table itself, with five LUT loads that copy the low 32 words of R_ACC into it.

Direct functions and LUT functions

function_type is 3 bits and names seven types.[AaQ §5.0]

CodeTypeEvaluated by
1identityDirect
2reluDirect
3relu6Direct
4genericLUT: sigmoid, tanh, gelu, softplus, elu, silu or window, whichever is loaded
5reciprocalLUT, with a guard for x = 0
6rsqrtLUT, with guards for x = 0 and x < 0
7exp2LUT

generic is one code for seven functions. The encoding does not say which one runs; the table contents do.

What the LUT holds

The stage keeps 256 entries of 17 bits (4352 bits) plus a 75-bit LUT metadata block that sets how inputs outside the table's range are handled.[AaQ §5.2] This LUT metadata is unrelated to a row's 16-bit metadata word.

BitsFieldMeaning
[7:0]max_exp_numLargest biased FP32 exponent inside the table's range; larger inputs are out of range.
[39:8]neg_cFP32 result for negative out-of-range inputs.
[71:40]pos_cFP32 result for positive out-of-range inputs.
[72]asymetricTable domain and address form. Encoding TBD.
[74:73]range_modeOut-of-range policy. Encoding TBD.

Source: AaQ §5.2.2.

Filling it: five LUT loads

The spec's instruction is LOAD lut_addr, in the AAQ slot. Each one copies a 1024-bit segment from R_ACC words 0–31 (32 × 32 bits) into the LUT. lut_addr 0–4 are used; 5–7 are reserved.[AaQ §5.2.1] The LUT load writes no XMEM and leaves R_ACC unchanged.

The spec then describes the segment layout twice, and the two descriptions disagree:

§5.2.1 and §5.2.2§6.3 pseudocode
Table layoutOne flat 4352-bit stream; entry i is stream bits [17i+16 : 17i]LUT[32k + j] = r_acc[j][16:0]
Entries per table segmentAbout 60; entries straddle segment boundaries32; word bits [31:17] ignored
Entries after segments 0–3240 complete, entry 240 split128: half the table
Segment 4Last 256 table bits, then LUT metadata at payload[330:256]LUT metadata only, at payload[74:0]

Only the flat reading fills all 256 entries with five loads, and only it matches the worked example in §5.2.2 (max_exp_num = r_acc[8][7:0]). The §6.3 pseudocode and summary table need correcting.[AaQ §6.3]

Unpack a segment both ways

The example words are built for the flat reading: entry i = (i × 0x101 + 0x40) & 0x1FFFF, and segment 4 carries max_exp_num = 133, neg_c = −1, pos_c = 1, range_mode = 1. Pick lut_addr 4 and compare the two LUT metadata lines.

Ordering hazards

You noted earlier that the LUT load must not run at the same time as other loads. The spec states no rule, so here is what can collide:

  • With ACTIVATE.QUANTIZE in the same word: impossible. Both sit in the AAQ slot, and a word has one instruction per slot.
  • With ACTIVATE.QUANTIZE between loads: a LUT function that runs after segments 0–2 reads a half-new, half-old table. The spec says nothing about it; the emulator needs a fault or a documented software rule.
  • With LD.* in the LOAD slot: no shared XMEM port. The LUT load reads R_ACC, not XMEM. The name clashes, though: the mnemonic standard is UNIT.OP and the LOAD slot is already called LOAD, so the proposal is AAQ.LUT.LD.
  • With ACC: AAQ sees the forwarded R_ACC, the ACC result of the same word (glossary: forwarded value). An ACC write in the same word changes what the LUT load copies.

The opcode costs a bit

The ISA's AAQ opcode is 1 bit today: NOP and ACTIVATE.QUANTIZE. A third instruction needs 2 bits. AAQ_SLOT_T_WIDTH goes from 9 to 10, and the whole VLIW word grows. That is a breaking change for the downstream RTL repo, which vendors the generated SystemVerilog package.[OQ-26]

Explain it back

In three sentences, tell the AaQ spec owner why the emulator cannot implement the LUT load bit-exactly from today's spec.

§5.2.1 packs the table as one flat 4352-bit stream with the LUT metadata at payload[330:256], while the §6.3 pseudocode takes the low 17 bits of each word (only 128 entries) and the LUT metadata from payload[74:0]. Even with the layout fixed, the spec does not say how an FP32 input selects an entry, nor what asymetric and range_mode mean (OQ-25). It also gives no ordering rule for an activation that runs between LUT loads.

What this means for the emulator

Today ACTIVATE.QUANTIZE has a 4-bit selector with 13 named functions (identity = 0 … window = 12), each computed with exact Python math, with α and the window bounds stored on the state.[ipu_isa/activations.py] [ipu_emu/activations.py] The spec's codes start at 1 and use 3 bits, so the two encodings differ even for identity. The plan agreed in the design session:

  • The LUT load stores bits exactly. The emulator keeps the 4352 table bits and the 75 LUT metadata bits as loaded, using the flat reading.
  • LUT functions use exact math for now. The kernel or harness declares which function is loaded, and generic, exp2, reciprocal and rsqrt evaluate it exactly. A bit-exact evaluator replaces this behind the same interface once indexing is specified.
  • Today's instruction stays for old kernels, in an emulator-only slot, with its 13 functions and 4-bit selector unchanged.
  • An ordering rule is needed for activations between LUT loads; a fault is the safest default.
Where the spec stops
  • §5.2.1 and §6.3 disagree on the table layout and on where the LUT metadata sits.
  • How an FP32 input becomes a LUT address, and the asymetric and range_mode encodings: TBD (OQ-25).
  • One 256-entry LUT serves four types, yet §5.0 writes LUT[function_type]. It is unclear whether exp2 and generic can be loaded together.
  • reciprocal(0) and rsqrt(0): the pseudocode returns inf, the table returns 0 (OQ-24).
  • How exact LUT bit patterns get into R_ACC is not described. They must pass through LD, MULT and ACC first.
  • lut_addr is described as selecting "8 segments"; only 5 exist.
