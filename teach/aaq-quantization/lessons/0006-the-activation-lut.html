The activation LUT and LOAD_LUT

AaQ computes three activations directly and four through one lookup table inside the stage. The kernel fills that table with five LOAD_LUT instructions, each copying the low 32 words of R_ACC.

Spec update (master 0511213)

The architecture spec (ARCH-stage-aaq-str.md §4.2–4.3.1) now defines the LUT load, a 46-bit LUT metadata block, the entry points and the special cases. It disagrees with the microarchitecture spec on the encodings, the special values and the LUT metadata (audit #5, #7–#12). This lesson follows the architecture spec.

Direct functions and LUT functions

activation_fn names seven types.[ARCH AaQ §4.3.1]

There is one LUT, holding one function at a time. generic is one code for any loaded function; the table contents decide what it computes. The microarchitecture spec numbers the same types 1–7 in a different order (audit #5).

What the LUT holds

The stage keeps 256 entries of 17 bits (4352 bits) and a 46-bit LUT metadata block that sets the table's range and what happens outside it.[ARCH AaQ §4.2.2] LUT metadata is unrelated to a row's 16-bit metadata word.

BitsFieldMeaning
[7:0]max_exp_numSets the table's range, 2max_exp_num; larger inputs are out of range.
[24:8]neg_c17-bit constant for negative out-of-range inputs.
[41:25]pos_c17-bit constant for positive out-of-range inputs.
[43:42]range_modeLUT version: 0 = positive x, 1 = negative x, 2 = 128 entries each side.
[44]neg_modeNegative out-of-range result: 0 = x, 1 = neg_c.
[45]pos_modePositive out-of-range result: 0 = x, 1 = pos_c.

Entries sit at linear steps across the range: step = 2max_exp_num / 256. Version 3 uses 2 × step and has two entries at zero, −0 and +0.[ARCH AaQ §4.2.3] The microarchitecture spec still has a 75-bit block with FP32 constants (audit #10).

Filling it: five LOAD_LUTs

LOAD_LUT lut_addr table_id table_offset copies one 1024-bit segment from R_ACC words 0–31 (payload[32j +: 32] = R_ACC[j]).[ARCH AaQ §4.2] The table is one flat 4352-bit stream:

lut_addrLoads
0–3Table bits [1024k + 1023 : 1024k]; entries straddle segment boundaries
4Table bits [4351:4096] in payload[255:0], LUT metadata in payload[301:256]
5–7Invalid

The operation never uses table_id or table_offset (audit #11). Operands that name a table and an offset usually mean an XMEM access.

Unpack a segment

Example: entry i = (i × 0x101 + 0x40) & 0x1FFFF; segment 4 carries max_exp_num = 2, range_mode = 2, neg_mode = pos_mode = 1. The last column assumes version 3 entries run from the most negative point up; the spec does not give the index order.

Ordering hazards

You noted earlier that the LUT load must not run at the same time as other loads. The specs state no rule. What can collide:

  • With ACTIVATE.QUANTIZE in the same word: impossible. Both sit in the AAQ slot, and a word has one instruction per slot.
  • With ACTIVATE.QUANTIZE between loads: a LUT function that runs after segments 0–2 reads a half-new table. The emulator needs a fault or a documented software rule.
  • With LD.* in the LOAD slot: the operation reads R_ACC, so it needs no XMEM port. If table_id and table_offset mean an XMEM read, LOAD_LUT would compete with the LOAD slot for the read port. That may be the conflict you meant.
  • With ACC: AAQ sees the forwarded R_ACC, the ACC result of the same word. An ACC write in the same word changes what the LUT load copies.

The name LOAD_LUT breaks the repo's mnemonic standard (UNIT.OP, no underscores); the repo-style name is AAQ.LUT.LD (audit #20).

The cost in the instruction word

The ISA's AAQ opcode is 1 bit today. A third instruction needs 2 bits; by position, NOP = 0, LOAD_LUT = 1, ACTIVATE.QUANTIZE = 2, unlike the microarchitecture spec's order (audit #12). With the architecture spec's operands, the AAQ slot grows from 9 bits to about 21 (lesson 8). Either change breaks the SystemVerilog package the downstream RTL repo vendors.

Explain it back

In three sentences, tell the AaQ spec owner why the emulator cannot evaluate the LUT bit-exactly yet, even though the layout is now settled.

The spec gives where each entry sits and which x it stands for, but not the 17-bit entry's number format or how a value between two entry points is computed. It also calls max_exp_num a biased FP32 exponent while §4.2.3 uses it directly as 2max_exp_num, and it does not say which index holds which point in version 3. Until those are fixed, the emulator stores the loaded bits exactly and evaluates the declared function with exact math.

What this means for the emulator

Today's ACTIVATE.QUANTIZE has a 4-bit selector with 13 named functions (identity = 0 … window = 12), computed with exact Python math.[ipu_isa/activations.py] [ipu_emu/activations.py]

  • LOAD_LUT stores bits exactly: the 4352 table bits and the 46 LUT metadata bits, using the flat layout.
  • LUT functions use exact math for now. The kernel or harness declares which function is loaded. A bit-exact evaluator replaces this behind the same interface once the entry format and interpolation are defined (audit #23).
  • The hardware instruction uses the architecture encodings 0–6 and its special cases.
  • The old instruction stays for old kernels, in an emulator-only slot, with its 13 functions and 4-bit selector unchanged.
  • An ordering rule is needed for activations between LUT loads; a fault is the safest default.
Where the spec stops
  • The 17-bit entry format and the interpolation between entry points are not defined (audit #23).
  • §4.2.2 calls max_exp_num a biased FP32 exponent; §4.2.3 and its examples use it as an unbiased power, 2max_exp_num.
  • The format of the 17-bit neg_c and pos_c is not defined, nor range_mode = 3.
  • Which entry index holds which point in version 3 is not stated.
  • LOAD_LUT's table_id and table_offset have no effect in its operation (audit #11).
  • No ordering rule for an activation between LUT loads, and no description of how exact LUT bit patterns reach R_ACC.
  • Encodings, special values and the LUT metadata differ from the microarchitecture spec (audit #5, #7–#10, #12).
