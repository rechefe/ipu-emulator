Back from XMEM: LD, MULT and expansion to FP32

The next layer reads AaQ's rows back. A load copies a row into a MULT register; MULT turns each byte into an FP32 value using the row's scale and the table's fe, then multiplies. No spec defines that expansion yet. This lesson proposes one and shows where it gets hard.

The round trip

AaQ quantizes→ ST.AAQ→ XMEM row + metadata word→ DRAM (optional)→ LD.MULT→ register + metadata→ MULT expands→ MULT_RES, FP32→ ACC

The metadata word stays with its row the whole way. The cache unit moves it to and from DRAM with the data (dram_rd_metadata, dram_wr_metadata).[cache unit §3] The dashed step is the one no spec covers.

What the loads do today

Each load copies one XMEM row, 128 elements, into a MULT-stage register.[slots/load.py]

InstructionDestinationRows heldRead by
LD.MULTR0 or R11 eachMULT.RC.VV, and MULT.VE/MULT.EE through Ra = R0 ++ R1, a 256-element cyclic window
LD.MULT.CYCLICR_CYCLIC quarter 0–3 (index 0, 128, 256, 384)4MULT.RC.*: a 128-element window at any element offset, wrapping at 512
LD.MASKR_MASKfirst 128 BThe lane mask: 1 bit per element, no scale

MULT then decodes each operand with the run's one element format and writes 128 products to MULT_RES, rounded once to the accumulator type: FP32 for every float format, INT32 for INT8.[slots/mult.py] [formats.py] The decode is the emulator's biased Ex from lesson 3. Nothing reads a scale.

The accumulator spec says FP8 multiplies "produce FP32 products — see the MULT stage".[ACC spec] There is no MULT-stage spec in docs/content/specs/.

The proposed expansion

Expansion is the lesson 1 decode, applied per element with the scale of the row the element came from:

Exponent fieldExpanded FP32 value
Exp < 2fe − 1±(1 + M/2fm) · 2s − 127 − Exp
Exp = 2fe − 1±(M/2fm) · 2s − 127 − 2fe + 2
  • s comes from the row's metadata word, so the register must keep it.
  • fe comes from the table format; in a dynamic table it comes from the row's dynamic_exponent bit instead (1 = E2M5, 0 = E1M6).
  • For fe ≤ 4, every expanded value is exact in FP32. For fe 5 or 6 and a small scale, the lowest binades fall below FP32's smallest subnormal, 2−149.

When the product is exact

An expanded element has at most 7 significant bits (1 + fm, and fm ≤ 6). Two of them multiply to at most 14 bits. An FP32 significand has 24 bits, so the product is exact whenever its magnitude lies in FP32's normal range, 2−126 to just under 2128.

  • Overflow: an operand is below 2s − 126, so a product overflows only when the two scales sum above about 380 (both rows near 263 or larger).
  • Underflow: products below 2−126 lose bits as FP32 subnormals; below 2−149 they become 0.

Inside that range, the only rounding between the two layers is AaQ's quantization and ACC's FP32 additions.

Expand and multiply

Try A = 07, fe 4, scale 254 and B the same: the product overflows. Try both scales at 10 with byte 00: the product flushes to 0.

Registers must carry metadata

If MULT expands, each register loaded from XMEM must keep the metadata word and the table format of every row it holds: one for each of R0 and R1, four for R_CYCLIC, one per quarter.

Windows make this hard. MULT.RC.* reads 128 elements from any offset, so a window can span two quarters loaded from different rows, with different scales. MULT.VE has the same problem across R0 and R1. Three options:

  • Per element: each element uses the scale of the quarter it came from. Exact, and existing access patterns keep working. Costs RTL a scale mux per element.
  • Fault on mismatch: a window spanning quarters with different metadata raises a fault. Cheap; restricts kernels.
  • One scale wins: the first quarter's scale applies to the whole window. Cheap, and silently wrong for the other part.

The per-element rule is the recommendation, with its RTL cost logged as an open question.

Which quarters a window reads

Try offset 0 (one quarter), 200 (quarters 1 and 2) and 448 (quarters 3 and 0, wrapping).

Scalar operands

  • MULT.RC.VE with an LR source multiplies by one element of Ra. That element has a row, so it has a scale: its register's metadata.
  • MULT.VE, MULT.EE, and MULT.RC.VE with a CR source decode the CR's low element bits in the run's format.[codecs.py, decode_cr_scalar] A CR has no metadata word, so a scaled CR scalar has no scale. It could hold an FP32 value, an emulator-style Ex byte, or a byte plus a scale. Nothing decides this yet.

Practice

The last two questions come from lessons 5 and 6.

Explain it back

In three sentences, describe what happens to an AaQ row between ST.AAQ and MULT_RES, naming where the scale and fe travel.

ST.AAQ writes the 128 bytes and the metadata word (scale, dynamic_exponent) to an XMEM row; the cache unit keeps them together, through DRAM if the table goes there. A load copies the row into R0, R1 or one R_CYCLIC quarter, and the register keeps the metadata word and the table's format, found from the load's table id. MULT expands each element with its own row's scale and fe, multiplies exactly in FP32, and writes MULT_RES for ACC.

What this means for the emulator

  • Registers gain metadata. R0, R1 and each R_CYCLIC quarter store a metadata word and a table format beside their bytes; the loads fill them.
  • A second decode path. MULT expands rows from AaQ tables with the scale-relative decode, and keeps today's codec for everything else, so legacy kernels and their goldens stay the same.
  • Windows decode per element. _r_cyclic_window and _ra_lanes in slots/mult.py pick each element's scale from the quarter or register it came from.
  • Decisions to settle: the window rule, how a CR scalar is scaled, and what an fe 5–6 underflow does.
Where the spec stops
  • No MULT-stage spec: the expansion, the register metadata and the products are all undefined.
  • No rule for a window that spans rows with different scales (R_CYCLIC quarters, or R0/R1 in Ra).
  • No encoding for a scaled CR scalar.
  • No behaviour for products that overflow or underflow FP32, or for expanded values below 2−149.
