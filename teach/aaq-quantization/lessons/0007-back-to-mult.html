Back from XMEM: LD, MULT and expansion to FP32

The next layer reads AaQ's rows back. A load copies a row into a MULT register; MULT turns each byte into an FP32 value using the row's scale and the fe its quantizion_format CR names, then multiplies. The MULT architecture spec specifies that expansion; this lesson walks through it and shows where it still gets hard.

Spec update (master 0511213)
  • A MULT spec exists: ARCH-stage-mult.md. §3.2.1 specifies the NX8-to-FP32 decode this lesson first proposed, and that each R0, R1 and R_CYCLIC slot keeps its own metadata.
  • Every MULT instruction gains a quantizion_format CR operand. Its layout differs from the AaQ one (spec audit #17).
  • MULT's metadata lists dynamic_static, which no spec writes (audit #18). ACTIVATE.QUANTIZE now stores the row itself (audit #1).

The round trip

ACTIVATE.QUANTIZE quantizes and stores→ XMEM row + metadata word→ DRAM (optional)→ LD.MULT→ register + metadata→ MULT expands→ MULT_RES, FP32→ ACC

The metadata word stays with its row the whole way. The cache unit moves it to and from DRAM with the data (dram_rd_metadata, dram_wr_metadata).[cache unit §3]

What the loads do today

Each load copies one XMEM row, 128 elements, into a MULT-stage register.[slots/load.py]

InstructionDestinationRows heldRead by
LD.MULTR0 or R11 eachMULT.RC.VV, and MULT.VE/MULT.EE through Ra = R0 ++ R1, a 256-element cyclic window
LD.MULT.CYCLICR_CYCLIC quarter 0–3 (index 0, 128, 256, 384)4MULT.RC.*: a 128-element window at any element offset, wrapping at 512

MULT then decodes each operand with the run's one element format and writes 128 products to MULT_RES, rounded once to the accumulator type: FP32 for every float format, INT32 for INT8.[slots/mult.py] [formats.py] The decode is the old emulator Ex that lesson 3 retires. Nothing reads a scale.

The MULT architecture spec defines the hardware: dequantize each NX8 element to FP32 with the format from quantizion_format and the vector scale, multiply, then mask.[ARCH MULT §1]

The specified expansion

ARCH MULT §3.2.1 specifies the lesson 1 decode, applied per element with the scale of the row the element came from:[ARCH MULT §3.2.1]

Exponent fieldExpanded FP32 value
Exp < 2fe − 1±(1 + M/2fm) · 2s − 127 − Exp
Exp = 2fe − 1±(M/2fm) · 2s − 127 − 2fe + 2
  • s comes from the row's metadata word, so the register must keep it.
  • fe comes from the quantizion_format CR operand: nx_format 1–7. nx_format = 0 means dynamic, and then fe comes from the row's dynamic_exponent bit (1 = E2M5, 0 = E1M6).
  • For fe ≤ 4, every expanded value is exact in FP32. For fe 5 or 6 and a small scale, the lowest binades fall below FP32's smallest subnormal, 2−149.

When the product is exact

An expanded element has at most 7 significant bits (1 + fm, and fm ≤ 6). Two of them multiply to at most 14 bits. An FP32 significand has 24 bits, so the product is exact whenever its magnitude lies in FP32's normal range, 2−126 to just under 2128.

  • Overflow: an operand is below 2s − 126, so a product overflows only when the two scales sum above about 380 (both rows near 263 or larger).
  • Underflow: products below 2−126 lose bits as FP32 subnormals; below 2−149 they become 0.

Inside that range, the only rounding between the two layers is AaQ's quantization and ACC's FP32 additions.

Expand and multiply

Try A = 07, fe 4, scale 254 and B the same: the product overflows. Try both scales at 10 with byte 00: the product flushes to 0.

Registers must carry metadata

The spec says R0, R1 and each 128-element slot of R_CYCLIC keep the metadata of the vector loaded into them: one word for each of R0 and R1, four for R_CYCLIC, one per quarter.[ARCH MULT §3.2.1]

Windows make this hard. MULT.RC.* reads 128 elements from any offset, so a window can span two quarters loaded from different rows, with different scales. MULT.VE has the same problem across R0 and R1. Three rules were possible; the spec picks the first ("each element uses the metadata of the register or slot that holds it"):

  • Per element: each element uses the scale of the quarter it came from. Exact, and existing access patterns keep working. Costs RTL a scale mux per element.
  • Fault on mismatch: a window spanning quarters with different metadata raises a fault. Cheap; restricts kernels.
  • One scale wins: the first quarter's scale applies to the whole window. Cheap, and silently wrong for the other part.

The per-element rule costs RTL a scale mux per element.

Which quarters a window reads

Try offset 0 (one quarter), 200 (quarters 1 and 2) and 448 (quarters 3 and 0, wrapping).

Scalar operands

  • MULT.RC.VE with an LR source multiplies by one element of Ra. That element has a row, so it has a scale: its register's metadata.
  • MULT.VE, MULT.EE, and MULT.RC.VE with a CR source decode the CR's low element bits in the run's format.[codecs.py, decode_cr_scalar] The spec takes a CR scalar from bits [7:0] and decodes it as NX8, but a CR has no metadata word, so the scalar has no defined scale.

Explain it back

In three sentences, describe what happens to an AaQ row between ACTIVATE.QUANTIZE and MULT_RES, naming where the scale and fe travel.

ACTIVATE.QUANTIZE writes the 128 bytes and the metadata word (scale, dynamic_exponent) to an XMEM row; the cache unit keeps them together, through DRAM if the table goes there. A load copies the row into R0, R1 or one R_CYCLIC quarter, and the register keeps the metadata word. MULT takes fe from its quantizion_format CR (or from dynamic_exponent when the format is dynamic), expands each element with its own row's scale, multiplies exactly in FP32, and writes MULT_RES for ACC.

What this means for the emulator

  • Registers gain metadata. R0, R1 and each R_CYCLIC quarter store a metadata word beside their bytes; the loads fill them.
  • One decode path. MULT decodes NX8 per ARCH MULT §3.2.1. The old emulator Ex goes (lesson 3); the 3 kernels that used it get new goldens.
  • A format operand. Every MULT instruction names a quantizion_format CR, so every kernel's MULT lines change mechanically.
  • Windows decode per element. _r_cyclic_window and _ra_lanes in slots/mult.py pick each element's scale from the quarter or register it came from.
  • Decisions to settle: how a CR scalar is scaled, what an fe 5–6 underflow does, which quantizion_format layout wins (audit #17), and whether metadata carries dynamic_static (audit #18).
Where the spec stops
  • The quantizion_format layout differs between the AaQ and MULT architecture specs (audit #17).
  • MULT's metadata has a dynamic_static bit no spec writes (audit #18).
  • A CR scalar is an NX8 byte with no scale.
  • NX8 NaN and inf: "TBD - ask Jacob" (audit #22).
  • No behaviour for products that overflow or underflow FP32, or for expanded values below 2−149.
